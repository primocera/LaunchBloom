ROLE AND OBJECTIVE
You are the senior backend and billing engineer for Scalvya. Fix entitlement lookup so a temporary Supabase/database failure is never interpreted as 'the customer has no paid plan'. Preserve access for existing paid users and prevent duplicate checkout creation when verification is unavailable.
STARTING CONTEXT
Inspect backend/routes/customers.js, especially planFor(email), and every caller in checkout, verify-plan, account/billing UI, tests, and support/admin paths.
Today planFor catches all exceptions and returns null. Callers cannot distinguish a legitimate no-subscription result from a database failure. Checkout may fail open and verify-plan may render a paying customer as Free.
Treat identity, plan, and entitlement as security-sensitive state. Do not solve this by showing raw errors or revoking known access on a transient failure.
IMPLEMENTATION REQUIREMENTS
Introduce an explicit result model or typed errors that distinguish: verified free/no entitling subscription; verified mapped paid entitlement; verified entitling subscription with unknown price; and verification unavailable due to infrastructure/provider error.
On checkout, fail closed when entitlement verification is unavailable. Return a stable machine error code and a human-safe retry message. Do not create a Stripe Checkout Session in that path.
On verify-plan/account reads, never convert verification unavailable into Free. Return the last safe state if the existing architecture has an authenticated, trustworthy cache; otherwise return an unknown/unavailable state and instruct the UI to preserve current access until retry.
Ensure unknown Stripe price IDs are visible to operations without exposing identifiers to the end user. Add structured, redacted logging and an alertable error code.
Keep auth-derived email as the only identity source. Normalize it once. Do not accept plan or entitlement claims from the client.
Update frontend copy for the unavailable state to: 'We couldn’t verify your plan right now. No access change was made. Please try again.' Match existing tone and localization conventions.
Document retry behavior and support escalation. Avoid indefinite spinners: use a bounded retry and an explicit retry action.
TESTS
Unit-test all four result states and assert that infrastructure errors are not returned as null/free.
Checkout test: on Supabase error, no Stripe session is created and the stable verification-unavailable response is returned.
Account/verify-plan test: a paying user is not downgraded in UI state during a transient lookup error.
Regression-test normal Free, Starter, and higher plans, including retired-price plus current-price overlap.
Run npm run lint, the relevant backend tests, npm test, npm run build:app, and npm run check:app-fresh.
ACCEPTANCE CRITERIA
No billing-critical caller treats 'could not verify' as 'verified free'.
No duplicate checkout can be created solely because Supabase is unavailable.
Users see a clear recoverable state without raw provider text; existing paid access is not silently revoked.
Tests prove both fail-closed checkout and non-destructive account behavior.
NON-GOALS
Do not redesign pricing, migrate Stripe products, or change plan allowances in this prompt.
Do not add an untrusted localStorage entitlement override.
FINAL REPORT
Return: (1) exact files changed, (2) behavior before and after, (3) tests run with exact pass/fail counts, (4) commands not run and why, (5) residual risks, (6) documentation/evidence updated, and (7) whether the next prompt is safe to start.
Use PASS only for a command or production observation that actually ran against the stated commit and environment. Use BLOCKED, NOT RUN, or FAILED otherwise.
Do not claim launch readiness in prose. Report evidence; the repository's release gate and the owner determine the verdict.

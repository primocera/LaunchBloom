# SC-P0-05 · Remove or harden legacy customer and portal endpoints

ROLE AND OBJECTIVE
Audit and remove or harden legacy billing endpoints that are not needed by the current frontend. The authenticated user—not request body/path input—must define billing identity, and billing portal redirects must be server-controlled.
TARGETS
POST /api/customers currently accepts a client-supplied email even when authentication exists.
GET /api/customers/:id/portal?returnUrl= accepts an arbitrary returnUrl and appears superseded by the account portal flow using the server application URL.
Search frontend, tests, docs, mobile/extension clients, and route registration to prove whether either endpoint has a legitimate caller before removal.
IMPLEMENTATION REQUIREMENTS
Prefer deleting unreachable legacy surface. If compatibility requires keeping it, derive email from req.userEmail, derive customer identity server-side, and reject any mismatch without revealing whether another account exists.
Allowlist customer metadata keys and values; never forward arbitrary request metadata to Stripe.
Use one canonical account portal endpoint. Its return URL must come from validated server configuration or a strict same-origin allowlist; reject protocol-relative URLs, alternate ports, encoded redirects, subdomain tricks, javascript/data schemes, and untrusted hosts.
Preserve CSRF/origin defenses appropriate to the existing auth model. Keep errors generic and audited.
Remove dead documentation and tests only after replacing them with security regression coverage.
TESTS
Attempt to create a customer for another email.
Attempt arbitrary external, protocol-relative, encoded, mixed-case, and localhost return URLs.
Valid account portal flow returns to the configured application URL.
Unauthenticated and cross-workspace requests fail.
Search confirms no remaining current client dependency on deleted routes.
ACCEPTANCE CRITERIA
No public route trusts client email/customer ID for billing ownership.
No open redirect exists in portal return handling.
Current account billing flow remains functional.
FINAL REPORT
Return: (1) exact files changed, (2) behavior before and after, (3) tests run with exact pass/fail counts, (4) commands not run and why, (5) residual risks, (6) documentation/evidence updated, and (7) whether the next prompt is safe to start.
Use PASS only for a command or production observation that actually ran against the stated commit and environment. Use BLOCKED, NOT RUN, or FAILED otherwise.
Do not claim launch readiness in prose. Report evidence; the repository's release gate and the owner determine the verdict.

ROLE AND OBJECTIVE
Refine Scalvya's public positioning and in-product narrative without changing the core wedge. Make the value obvious in seconds, show the campaign workflow concretely, and replace generic AI claims with code-native product proof.
IMMUTABLE POSITIONING
Primary promise: 'Turn one offer into a launch-ready campaign.'
Primary ICP: B2B freelancers and boutique agencies who repeatedly turn an offer into coordinated launch assets. Solo founders are secondary.
Product story: Brand Profile → Campaign Brief → Create → Review → Library → Export.
Five creation paths: Website, Email, Social, Ads & Creative, SEO Ideas.
CONTENT CHANGES
Shorten hero support copy to one concrete outcome and one trust qualifier. Keep one primary CTA and one low-risk secondary CTA/sample path.
Show a realistic before/after or campaign packet assembled from deterministic fixture data in the repository: one offer input, then coordinated website/email/social/ad/SEO-idea outputs with Review statuses. Clearly label it as an example, not a customer result.
Explain what is coordinated across outputs—offer, audience, angle, proof, CTA, tone—rather than saying merely 'AI writes everything'.
Make Review and Ready to export visible in the marketing proof. Clarify Published is user-managed status, not a publishing integration.
Keep trial truth: workspace setup/editing is free; the three-day trial starts on first generation if that is the actual enforced behavior. Show exact plan/charge facts from the server catalog rather than duplicated hard-coded copy.
Remove unsupported time savings, ROI, customer counts, testimonials, logos, and security/compliance claims. Add real evidence only when verified and attributable.
Tighten FAQ around who it is for, what export means, whether it publishes, SEO limitation, data handling, trial start, and cancellation.
UX REQUIREMENTS
Maintain mobile readability, semantic heading order, contrast, keyboard navigation, reduced motion, and fast LCP.
Do not add heavy video or large image assets. Prefer code-native HTML/CSS example panels using existing components/tokens.
Keep landing content consistent with onboarding, dashboard, studios, paywall, and lifecycle email copy.
TESTS AND REVIEW
Add content contract tests for forbidden claims and trial/publishing/SEO qualifiers.
Run public E2E, accessibility checks available in repo, lint, unit tests, build, and bundle freshness.
Provide a before/after copy table and screenshots from local preview; label browser work BLOCKED if unavailable.
ACCEPTANCE CRITERIA
A first-time visitor can identify the target user, problem, workflow, output, limitation, and CTA without scrolling through generic AI language.
All proof is demonstrable from actual product behavior or clearly labeled example data.
No product claim exceeds the implemented capability.
FINAL REPORT
Return: (1) exact files changed, (2) behavior before and after, (3) tests run with exact pass/fail counts, (4) commands not run and why, (5) residual risks, (6) documentation/evidence updated, and (7) whether the next prompt is safe to start.
Use PASS only for a command or production observation that actually ran against the stated commit and environment. Use BLOCKED, NOT RUN, or FAILED otherwise.
Do not claim launch readiness in prose. Report evidence; the repository's release gate and the owner determine the verdict.

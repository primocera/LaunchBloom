PASTE INTO CLAUDE CODE
ROLE AND OBJECTIVE
Build a release-grade billing contract matrix and automated integration/E2E coverage against a seeded non-production environment. Prove that UI, API, database records, usage allowance, checkout prevention, and Stripe-webhook state agree.
REQUIRED SCENARIOS
Verified Free; eligible first trial; already-used trial; active current plan; active retired price; retired plus current overlap; past_due; cancel_at_period_end before expiry; fully canceled/expired; unknown price; foreign product; database outage; replayed/out-of-order webhook; checkout idempotency; portal return.
For each scenario record expected account label, allowed AI actions, checkout behavior, trial eligibility, export access, and user-facing message.
IMPLEMENTATION REQUIREMENTS
Create deterministic test fixtures/builders with redacted synthetic identities. Do not use real customer accounts.
Make auth E2E refuse to run against production or an unrecognized base URL/database project.
Add explicit assertions for fail-closed verification unavailable, no duplicate Stripe session, no entitlement from foreign products, and stable cancellation behavior.
Keep any provider-mocking boundary honest. Mark tests that use Stripe test mode versus pure mocks; do not call a mock an observed live result.
Write a concise matrix document generated from or cross-checked against test fixtures so expectations cannot drift silently.
EXECUTION
Run local unit/integration tests first.
Run npm run test:e2e:auth only against the approved seeded non-production target. If credentials or browser are missing, stop and report BLOCKED with exact prerequisites.
Never create live charges, trials, or production customers.
ACCEPTANCE CRITERIA
All named states have explicit expected behavior and automated coverage at the correct layer.
The current commit has authenticated E2E evidence or a truthful blocker; no stale candidate evidence is reused.
Failure states preserve user trust and billing correctness.
FINAL REPORT
Return: (1) exact files changed, (2) behavior before and after, (3) tests run with exact pass/fail counts, (4) commands not run and why, (5) residual risks, (6) documentation/evidence updated, and (7) whether the next prompt is safe to start.
Use PASS only for a command or production observation that actually ran against the stated commit and environment. Use BLOCKED, NOT RUN, or FAILED otherwise.
Do not claim launch readiness in prose. Report evidence; the repository's release gate and the owner determine the verdict.

ROLE AND OBJECTIVE
Implement privacy-conscious product analytics and an operator scorecard that measures Scalvya's real value loop, not vanity page views. Use it to run a controlled 10–20 user ICP beta and make expand/iterate/stop decisions.
EVENT MODEL
brand_profile_completed; campaign_brief_completed; first_generation_started/completed/failed; first_asset_reviewed; first_asset_ready_to_export; first_export; campaign_reached_ready; second_campaign_created; workspace_returned; trial_started; subscription_started/canceled.
Derived metrics: time to first reviewed asset, time to first export, campaign completion rate, retry/failure rate by studio, second-campaign rate, D1/D7/D30 workspace return, trial-to-paid conversion, paid retention, and export frequency per active workspace.
PRIVACY AND DATA QUALITY
Do not send offer text, campaign briefs, generated copy, emails, brand voice text, user email, or raw identifiers to analytics.
Use stable pseudonymous workspace/user IDs according to existing consent/privacy policy. Define event schema/version, idempotency/deduplication, environment, source, timestamp, and success/failure reason taxonomy.
Exclude staff/test/demo accounts from product KPIs with an auditable rule. Do not manipulate conversion denominators.
OPERATOR SCORECARD
Create a weekly cohort view for the capped beta: invited, activated, first reviewed asset, first export, campaign ready, second campaign, paid, retained, canceled, and top failure reasons.
Define provisional thresholds before collecting results. Example: expand only when the majority of activated target users reach a reviewed asset, generation failure is low, no billing-severity incident occurs, and qualitative interviews confirm the coordinated campaign saves meaningful rework. Mark thresholds as hypotheses, not market facts.
Add a short interview guide: previous workflow, time/rework, point of confusion, asset quality after review, willingness to pay, repeated use case, and what would cause cancellation.
TESTS
Schema tests for required/forbidden fields.
Duplicate/retry events do not inflate milestones.
No content/PII in captured payload fixtures.
Funnel calculations use mutually consistent denominators.
Analytics failure never blocks core product use or leaks data.
ACCEPTANCE CRITERIA
The team can answer whether users reached the paid value loop and returned to repeat it.
The scorecard separates product quality, technical failure, and acquisition quality.
No fabricated benchmark or launch claim is introduced.
FINAL REPORT
Return: (1) exact files changed, (2) behavior before and after, (3) tests run with exact pass/fail counts, (4) commands not run and why, (5) residual risks, (6) documentation/evidence updated, and (7) whether the next prompt is safe to start.
Use PASS only for a command or production observation that actually ran against the stated commit and environment. Use BLOCKED, NOT RUN, or FAILED otherwise.
Do not claim launch readiness in prose. Report evidence; the repository's release gate and the owner determine the verdict.

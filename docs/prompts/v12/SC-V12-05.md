# SC-V12-05 · Scalvya — Move launch-critical checks into a reproducible release workflow

**Run after:** SC-V12-04.
**Primary risk removed:** most launch evidence is local and can drift from the exact commit
deployed to users.

## Prompt

Create a reproducible, fail-closed Scalvya release-candidate workflow without exposing production
secrets.

Goals:
- A reviewer can identify the exact candidate SHA, bundle and evidence.
- A green ordinary CI run cannot be mistaken for full launch approval.
- Browser/export checks that protect the paid experience are not left as undocumented local-only
  claims.

Implement:
1. Audit .github/workflows, package scripts, launch-state validation and bundle freshness checks.
2. Keep a lean normal PR workflow, but add a dedicated manually triggered or release-branch
   workflow that runs: npm ci; lint; unit/contract/safety tests; production frontend build;
   stale-bundle check; public Playwright suite; DOCX/PDF/ZIP export integrity; launch-state
   integrity; authenticated E2E when the required non-production secrets are available.
3. In release-candidate mode, a missing required environment or any required skipped test must
   fail.
4. Upload raw evidence artifacts named with candidate SHA and workflow run ID. Do not upload
   secrets, database dumps or user content.
5. Ensure passed_ci is permitted only when the exact command appears in CI and evidence identifies
   the candidate SHA.
6. Detect code drift between candidate and HEAD. Documentation-only evidence commits may be
   exempt only through an explicit allowlist that can never include app/, app-src/, backend/,
   api/, e2e/, config or package files.
7. Add tests preventing future expansion of the exempt path set into product code.
8. Keep owner-only live checks separate. CI must display them as NOT RUN when unavailable, not
   pass.

Do not declare a new release candidate in this prompt. This prompt builds the machinery;
SC-V12-08 performs the freeze after all product changes are merged.
